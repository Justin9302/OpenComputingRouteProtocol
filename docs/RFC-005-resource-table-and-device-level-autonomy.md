# RFC-005: 设备级自治与资源表（Device-level Autonomy & Resource Table）

- **状态**: Draft
- **作者**: Open Compute Router Contributors
- **创建日期**: 2026-08-07
- **最后更新**: 2026-08-07

## 1. 摘要

本 RFC 定义 OCR 协议的**设备级自治（Device-level Autonomy）**模型：电力与算力数据在 **Hub/Switch/Router 等网络设备层**处理，而非集中到任何第三方中央平台；每台独立设备接入网络后，**配置一个接口地址即可被动接收数据**，并**独立维护一张资源表（Resource Table）**——一张与路由表（Routing Table）同构的「算力 × 能源」资源视图。由此构成一个**不依赖、不受任何第三方影响**的自洽体系，安全性内生于架构本身。

## 2. 设计动机

- **中央平台的脆弱性**：集中式调度依赖第三方平台聚合数据 → 单点故障、信任链外延、数据主权旁落、平台政策绑架业务。
- **网络即控制平面**：Hub/Switch/Router 天然是网络的一部分，接入网络即可通信；在其上处理电力数据无需额外引入第三方数据中介。
- **路由思想的自然迁移**：路由表回答"数据包往哪走"，资源表回答"计算任务何时、在哪儿、用什么电跑"——网络设备已经证明了这张表可以在分布式、自治、无中央控制器的前提下收敛（BGP/OSPF 先例）。
- **安全性来自独立性**：不受任何第三方影响的体系，攻击面最小、无单点、无外延信任依赖。

## 3. 核心概念

### 3.1 资源表（Resource Table）

与路由表同构，但面向「计算 + 能源」：

| | 路由表（Routing Table） | 资源表（Resource Table） |
|---|---|---|
| 表项 | 目的网络 → 下一跳/出接口 → 度量 | 资源标识 → 状态 → 度量 |
| 度量 | 距离、开销、带宽 | 电价、绿电比例、可用算力、SOC、时延、碳排放 |
| 决策 | 数据包走哪条路 | 任务何时/在哪儿/用什么电跑 |
| 维护 | 每台设备独立维护 + 协议扩散 | 每台设备独立维护 + 资源通告扩散 |

每条资源表项（Resource Entry）包含：

| 字段 | 说明 | 示例 |
|------|------|------|
| `resource_id` | 资源唯一标识 | `server/ap-southeast-02` |
| `resource_type` | 资源类型 | `compute` / `storage` / `energy_grid` / `battery` |
| `status` | 可用状态 | `up` / `degraded` / `down` |
| `price_per_mwh` | 电价（本币/MWh，可为负） | `-25.0` |
| `green_ratio` | 绿电比例（0~1） | `0.72` |
| `avail_compute` | 可用算力（如可用 GPU 数/显存） | `{ "gpu": 8, "vram_gb": 640 }` |
| `battery_soc` | 储能剩余电量（0~1，可选） | `0.85` |
| `latency_ms` | 到本设备的时延 | `35` |
| `co2_intensity` | 碳排放强度（可选） | `0.21` |
| `ttl` | 表项有效期 | `300s`（过期即失效） |
| `trust_anchor` | 身份来源（SPIFFE ID） | `spiffe://open-compute-router.org/server/ap-southeast-02` |

> 规范见 [spec/resource-table.schema.json](../spec/resource-table.schema.json)。

### 3.2 设备级被动接收（Passive Data Ingestion）

- 每台设备（Hub / Switch / Router / 算力节点）接入网络，**配置一个接口地址（listen endpoint）**；
- 数据源（AEMO 电价、节点状态、储能 SOC、电网需求响应事件）通过**发布-订阅 / 推送**模型到达设备，设备**被动接收**，无需主动轮询，也无需任何第三方平台转发；
- 设备本地解析 → 校验（来源身份 mTLS）→ 更新本地资源表。

```text
[电网开放数据 / 算力节点状态 / 储能状态]
       │  发布-订阅推送（配置接口地址即接收）
       ▼
[Hub / Switch / Router 设备层]
       │  被动接收 → 校验 → 更新本地资源表（类似路由表）
       ▼
[调度决策]  基于本地资源表 + SLA Tier 决定任务执行时机与位置
```

### 3.3 分布式扩散（Resource Advertisement）

- 设备间通过**资源通告（Resource Advertisement）**交换资源表项，机制对齐经典路由协议：
  - 类似 **BGP**：每个自治域维护本地资源表，向邻居通告"可达资源"，策略可控；
  - 类似 **OSPF/LS**：链路状态扩散，拓扑变化自动收敛；
- **无中央控制器**：任一设备失效，邻居表项过期后由其他通告路径收敛，整体不中断。

## 4. 安全性论证（为什么独立才安全）

| 维度 | 集中式（第三方平台） | 设备级自治（本设计） |
|------|---------------------|----------------------|
| 单点故障 | 平台宕机 = 全体中断 | 分布式资源表，无单点 |
| 信任链 | 信任第三方平台（外延） | 设备间直连 mTLS，信任链不外延 |
| 数据主权 | 数据经第三方聚合 | 资源表在设备本地维护，数据不出域 |
| 平台绑架 | 受平台政策/费率/关停影响 | 不受任何第三方运营政策影响 |
| 攻击面 | 中央系统是最高价值目标 | 攻击面分散，无单一蜜罐 |

- 资源通告携带 `trust_anchor`（SPIFFE ID），接收方按 RFC-003 零信任模型验证，拒绝无身份来源的表项；
- 调度决策基于**本地资源表 + 公开市场数据**，不涉及企业私有数据（与 RFC-004 §6 一致）；
- 被动接收模型天然符合最小权限：设备只暴露一个监听接口，不向外主动请求第三方。

## 5. 与三层架构的关系

```text
[用户层 / AI Agent]          声明算力意图（MCP）
       ▼
[Hub 层 / 控制平面]          ← 设备级自治：可部署于边缘 Router/Switch 或独立 Hub 设备
       │                       · 维护本地资源表（替代"中央数据库"）
       │                       · 被动接收电力/算力数据
       │                       · 下发调度指令（依据本地资源表 + SLA Tier）
       ▼
[Server 层 / 执行平面]       执行任务 → 上报状态（回写资源表项）
       ▼
[算力与电力资源池]            GPU/NPU/微电网/储能（通过资源通告进入各设备资源表）
```

- **Hub 层 = 设备级控制平面**：资源表是其核心数据结构，替代任何形式的中央数据库；
- **Server 层 = 执行平面 + 数据源**：状态上报即资源表项更新；
- **Switch/Router = 天然载体**：电力数据在它们之上处理，配置接口地址即接入。

## 6. 与既有 RFC 的关系

- RFC-001（三层架构）：本 RFC 将 Hub 层明确为**设备级控制平面**，资源表为核心数据结构；
- RFC-002（SLA Tiering）：调度决策依据本地资源表，而非中央聚合视图；
- RFC-003（零信任）：资源通告带 SPIFFE 身份，mTLS 验证；被动接收符合最小权限；
- RFC-004（能源接入）：能源插件（AEMO 等）可在设备层实现，数据以发布-订阅方式被动到达。

## 7. 演进原则

- **协议先行，代码渐进**：先以本 RFC 固化资源表结构，再实现参考模拟器；
- **向后兼容**：新增资源类型/度量字段不得破坏既有表项解析；
- **先单域，后互联**：先在一台设备上验证资源表 + 被动接收，再做多设备通告扩散（BGP/OSPF 式）。
