# 协议改进待办清单

> **创建日期**: 2026-09-11
> **状态**: 活跃 — 跟踪协议设计层面的已知问题与改进项
> **原则**: 协议是跑出来的不是写出来的。P0 项在阶段一开发前定下来，其余随真实运行经验逐步修订。

## 已确认改进项

### P0 — 阶段一开发前必须定下来

#### P0-1: 补 RFC-006 任务执行与生命周期协议

**问题**: 现有协议定义了"任务怎么声明""资源怎么描述""电价怎么接入"，但没有定义 Hub 和 Server 之间的任务执行交互。没有这个，端到端任务只能用私有接口，协议名存实亡。

**需要定义的内容**:
- 任务下发接口（建议 gRPC 流式，支持状态推送）
- 任务状态机：`pending → assigned → running → completed / failed / preempted`
- 任务数据/模型/结果的传输方式（对象存储引用 vs 直接传输）
- 抢占与断点续传的消息格式
- Server 向 Hub 上报状态的机制

**影响范围**: 阶段二 Hub/Worker 开发的基础

**计划**: 阶段一第 1-2 周期间起草 RFC-006 草案，阶段二开发前定稿

**状态**: ✅ 草案已完成，见 [RFC-006-task-execution-protocol.md](RFC-006-task-execution-protocol.md)

---

#### P0-2: 澄清 Hub 角色（逻辑角色 vs 物理中心）

**问题**: RFC-001 说 Hub 是"控制平面"，RFC-005 说"无中央控制器""不受任何第三方影响"，两者有张力。如果 Hub 是必须的，它不就是中央控制器吗？

**澄清方向**:
- Hub 是一个**逻辑角色**，不是物理中心
- 任何设备（包括 Server 节点自己）都可以运行 Hub 功能
- 小规模部署：中心化 Hub（简单）
- 大规模部署：分布式，调度决策基于本地资源表，Hub 只是"帮用户提交任务的那个节点"
- 在 RFC-001 和 RFC-005 中补充说明，消除矛盾

**影响范围**: 代码组织结构、阶段一原型的架构设计

**计划**: 阶段一第 1 周修订 RFC-001 和 RFC-005

**状态**: ✅ 已完成。RFC-001 §3 增加 Hub 角色说明，§3.2 补充三种部署形态（中心化/分布式/嵌入式）；RFC-005 §3.2 增加"无中央控制器"澄清，§5 重写与三层架构的关系。

### P1 — 阶段二开发前完成

#### P1-1: 澄清并统一 `price_ceiling` 语义

**设计意图（发起人确认）**:
用户声明**时间成本**（SLA Tier / max_completion_time）和**资金成本**（price_ceiling）双约束，系统在约束内进行资源匹配与调度，寻找最优执行方案。

**当前问题**:
- `compute-intent.schema.json` 描述为"愿意支付的最高单价（货币单位/任务）"——含义模糊
- `demo-30s.py` 中把它当成了"电价阈值"（AUD/MWh），与设计意图不符
- 算力价格和电力价格是两个不同维度，混为一谈

**改进方案**:
- `price_ceiling` 明确定义为**任务总预算上限**（本币，如 AUD）
- 调度器内部逻辑：
  1. 预测不同时段、不同节点的执行总成本（电力成本 + 算力服务费）
  2. 在时间窗口内筛选满足预算的执行方案
  3. 选择最优方案（最低成本 / 最高绿电比例 / 最早完成）
- 电价是调度器的内部输入，不直接暴露给用户
- 增加 `cost_optimization` 字段，让用户选择优化目标（min_cost / max_green / fastest）
- 增加 `currency` 字段，默认 AUD

**需要更新的文件**:
- `spec/compute-intent.schema.json` — 修改 price_ceiling 描述，增加 cost_optimization 和 currency
- `docs/RFC-002-sla-tiering.md` — 补充 §4.4 预算约束调度语义
- `examples/demo-30s.py` — 修正使用方式

**计划**: 阶段二第 1-2 周完成

**状态**: ✅ 已完成。schema 已更新（price_ceiling 改为任务总预算，新增 cost_optimization 和 currency）；RFC-002 新增 §4.4 预算约束调度；demo-30s.py 已修正并验证运行通过。

#### P1-2: 资源表增加算力描述字段

**问题**: `avail_compute` 只有 `gpu_count` 和 `vram_gb`，无法区分 H100 和 3090（算力差一个数量级），也无法满足分布式训练的网络需求。

**需要增加的字段**:
- `gpu_model`：GPU 型号字符串（如 "H100-80GB", "A100-40GB", "RTX3090"）
- `compute_capability`：计算能力描述（FP8/FP16/FP32 TFLOPS，可选）
- `network_bandwidth_gbps`：节点网络带宽（分布式训练需要）
- `cpu_cores` / `ram_gb`：CPU 和内存（数据预处理任务需要）

**需要更新的文件**:
- `spec/resource-table.schema.json`
- `docs/RFC-005-resource-table-and-device-level-autonomy.md`

**计划**: 阶段一第 2 周（资源表重构时）同步更新

**状态**: ✅ 已完成。schema 已扩充 gpu_model、compute_capability、network_bandwidth_gbps、cpu_cores、ram_gb 字段；RFC-005 资源表项表格已更新。

### P2 — 有真实运行经验后修订

#### P2-1: SLA 分级引入"策略组"概念

**问题**: T0-T10 共 11 级，但相邻等级调度策略差异很小（T3/T4/T5 都是"避开尖峰"，T8/T9/T10 都是"等低价"），每个等级单独实现调度逻辑不经济。

**改进方向**:
- 保留 T0-T10 的细粒度声明（用户表达更精确）
- 调度实现按**策略组**归类：
  - **实时组**（T0-T2）：立即执行，容忍峰值电价
  - **交互组**（T3-T5）：可短暂排队，避开尖峰
  - **批处理组**（T6-T7）：可被抢占，优先绿电时段
  - **离线组**（T8-T10）：仅在低价/负电价时段执行
- 每个策略组一套调度逻辑，组内按 Tier 调整参数（如等待时长、抢占阈值）

**计划**: 阶段二调度器实现时采用策略组设计，RFC-002 后续补充

---

#### P2-2: compute-intent 增加 `estimated_duration` 字段

**问题**: 调度器需要知道任务预计执行多久，才能判断能否在低价窗口内跑完。需要 10h 的任务和需要 1h 的任务，即使都是 T9，调度策略也不同。

**改进方向**:
- 增加 `estimated_duration` 字段（格式同 max_completion_time，如 "2h"）
- 用户可填，不填时调度器按任务类型估算（或取保守值）
- 调度器用此字段 + 电价预测，计算各候选时段的总成本

**计划**: 阶段二第 2 周随 Hub 调度器实现

#### P2-3: 能源插件接口细化

**问题**: `energy-plugin.interface.yaml` 只有三个数据结构，缺少插件注册、推送频率、预测vs实时区分、多区域处理等定义。

**需要补充**:
- 插件注册与发现机制
- 数据推送频率规范（实时电价 5min？预测 24h 滚动？）
- 实时数据 vs 预测数据的区分字段
- 多区域/多节点支持
- 数据质量/置信度字段

**计划**: 阶段三接 ComAp 前细化（有真实插件实现经验后写更靠谱）

#### P2-4: 资源表增加资源预留机制

**问题**: 多个 Hub 同时调度时，可能超额分配同一节点的算力。当前只有"可用量"，没有"已分配/预留量"。

**改进方向**:
- 增加 `reserved_compute` 或 `allocated_compute` 字段
- Hub 调度成功后在资源表中标记预留
- 任务完成/失败后释放预留
- 分布式场景下需要考虑预留的一致性（可先简化为单 Hub 场景）

**计划**: 阶段二后期，多任务并发时遇到实际问题再实现

---

#### P2-5: 资源表 TTL 老化改为衰减式

**问题**: 当前 TTL 到期直接删除表项，网络闪断可能导致节点被误判为下线，引起调度抖动。

**改进方向**:
- 引入"软状态"：连续 N 次（如 3 次）收不到通告才标记 `degraded`
- 再经过更长时间才标记 `down` 并删除
- 类似 BGP 的 hold timer 机制

**计划**: 阶段一多节点测试时观察是否有抖动问题，有则改进

---

#### P2-6: 租户优先级与账户分级

**背景**: 企业用户需要账户分级机制。高优先级账户默认实时调度，低优先级账户默认分钟级/低能源价格。这是企业版差异化定价和资源争抢裁决的基础。

**设计原则**:
- 协议层只定义"怎么传递优先级信息"，不定义"谁是 gold 谁是 economy"（后者是商业决策，写死在协议里会损害中立性）
- 租户优先级（账户级）与 SLA Tier（任务级）是两个维度，联合决定调度优先级
- 开源版 Hub 可忽略此字段（所有租户一视同仁），企业版 Hub 实现分级策略

**改进方向**:
- 在 `compute-intent.schema.json` 中增加可选字段 `tenant_priority`（enum: `gold` / `standard` / `economy`，默认 `standard`）
- RFC-002 补充"租户优先级与任务 SLA 的联合调度"说明：
  - 调度优先级 = f(任务 SLA Tier, 租户优先级)
  - 高优先级租户的低优任务，可能先于低优先级租户的高优任务调度
  - 高优先级租户的任务不可被低优先级租户抢占
- 企业版 Hub 可实现的分级策略（不写进协议）：
  - Gold：默认 T1-T2，调度权重高，不可被抢占，最高可声明 T0
  - Standard：默认 T4-T5，可被 Gold 抢占，最高可声明 T2
  - Economy：默认 T7-T9，可被任何高优先级抢占，最高可声明 T5

**影响范围**: `spec/compute-intent.schema.json`、`docs/RFC-002-sla-tiering.md`

**计划**: 阶段二 Hub 调度器实现时预留字段和权重逻辑；具体企业分级策略等有真实企业客户后再细化

#### P2-7: 位置感知调度（网络亲和性）

**背景**: 用户在不同网络环境（公司/家/公共网络）下，应自动优先使用就近的或自己部署的算力节点。类似手机在 WiFi 和蜂窝网络间自动切换。对数据主权要求高的用户尤其重要。

**设计原则**:
- 网络检测是客户端的事（检测 WiFi SSID / IP 段 / 网关），协议层不定义检测机制
- 协议层提供"网络亲和性调度"能力，让客户端能表达"优先某区域节点"
- 与现有 `latency_ms`（资源表）和 `security_level`（intent）协同工作

**改进方向**:
- `compute-intent.schema.json` 增加可选字段 `network_affinity`（字符串，如 "office"、"home"），表达优先的网络区域
- `resource-table.schema.json` 增加可选字段 `network_zone`，标记节点所属网络区域
- 调度器逻辑：有 `network_affinity` 时优先选同 zone 且 latency 最低的节点；同 zone 无可用节点时回退（除非 security_level 强制限制）
- 客户端维护"已知网络→network_zone"映射，提交任务时自动填入 `network_affinity`

**影响范围**: `spec/compute-intent.schema.json`、`spec/resource-table.schema.json`、调度器实现

**计划**: schema 字段现在预留；调度器匹配逻辑阶段二实现；客户端网络检测等有真实多节点部署后再做

**状态**: ✅ schema 字段已预留

#### P2-8: 数据敏感度分级与脱敏管道

**背景**: 数据主权要求高的用户（金融、医疗、政务、企业核心数据）需要数据不出域、自动敏感度检测、脱敏处理和审计留痕。这是企业版的核心卖点之一。

**设计原则**:
- 协议层定义数据敏感度的声明与约束字段
- 自动检测、脱敏算法、DLP 集成是实现层（企业版）的事，不写进协议
- 与 RFC-003 安全模型的 `security_level` 协同：敏感度高 → 强制 private_only + 脱敏

**分层认定设计（已确认）**:
采用"客户端引导，服务端强制"的分层设计，参考 DLP/Kubernetes/AWS IAM 的行业普遍做法：

- **客户端（终端插件，如 DeepSeek Harness 插件）**：做前置引导
  - 提供界面让用户选择优先级、时间窗口、网络亲和性
  - 自动扫描本地输入文件，检测潜在敏感信息（PII、医疗数据等），提示用户
  - 将用户选择和检测结果填入 Compute Intent 对应字段
  - **性质：建议性的**，用户可以调整

- **Hub（服务端）**：做最终强制认定
  - 对任务输入数据做自动 DLP 检测
  - 比较 Hub 检测结果与用户声明的敏感度
  - **若 Hub 检测到的敏感度高于用户声明，以 Hub 为准，强制升级**
  - 按最终敏感度级别强制执行路由约束（high→private_only，critical→confidential）
  - 记录完整审计日志

- **协议层**：只定义字段和约束规则，不规定检测算法
  - 定义 `data_sensitivity`、`data_masking_required`、`data_residency` 等字段
  - 定义强制约束（如 high 级别必须 private_only）
  - 规定"服务端检测结果优先于客户端声明"的原则

**为什么不能只信客户端**: 客户端声明可被用户手动修改或绕过；不同客户端检测能力参差不齐；合规要求必须有服务端强制校验和审计。类比：机场值机柜台可以帮你选座位，但登机口必须核验登机牌和身份。

**改进方向**:
- `compute-intent.schema.json` 增加可选字段：
  - `data_sensitivity`（enum: `low` / `medium` / `high` / `critical`）：数据敏感度分级，可由用户声明或 Hub 自动检测后填入
  - `data_masking_required`（boolean）：是否要求脱敏管道，high/critical 默认 true
  - `data_residency`（object）：数据地域/网络约束，含 `network_zone`、`country`、`allow_cross_zone`
- 调度器强制约束：high/critical 敏感度只能路由到 private_only 节点，且节点必须支持脱敏管道
- 企业版可实现：自动敏感度检测（DLP/NLP）、脱敏管道（替换/匿名化/加密）、数据分离（不同部分路由到不同节点）、合规审计报告

**影响范围**: `spec/compute-intent.schema.json`、RFC-003 安全模型（已补充 §5 数据敏感度分级与分层认定）、企业版 Hub、客户端插件

**计划**: schema 字段现在预留；RFC-003 已补充分层设计；自动检测与脱敏管道等有真实企业客户需求后再做；DeepSeek Harness 插件列入阶段四开发

**状态**: ✅ schema 字段已预留；✅ RFC-003 §5 已补充分层设计；✅ 发展计划已列入插件开发

#### P2-9: 客户端敏感度清单（Manifest）与环境证明

**背景**: Hub 做 DLP 检测需要读取数据内容，但高敏感数据用户不希望数据离开本地。需要一种机制让客户端在本地完成扫描，Hub 验证扫描结果的可信度而不重复扫描内容。

**设计方案（已确认）**:

**Manifest 清单文件**:
- 插件本地扫描后生成 `.ocr_manifest.json`，放置于数据集根目录
- 包含：每个文件的敏感度级别、SHA256 哈希、检测到的敏感类型（不含原文）、扫描时间、插件版本
- 不使用文件系统 xattr（跨平台和网络传输中易丢失），用随数据集传输的 JSON 文件
- Hub 优先读 manifest，抽样验证哈希，验证通过则不扫描内容
- 无 manifest 或验证失败时，Hub 兜底扫描

**三层环境证明**:
- **第一层（开源版，必须）**：插件签名验证 + 版本校验 + 时间戳防重放
- **第二层（企业版）**：环境健康声明（OS 版本、root/越狱检测、调试器检测、规则库完整性）
- **第三层（远期）**：TPM 2.0 远程证明，仅对 confidential 级别任务启用

**信任分级**:
- 高信任（≥80分）：完全信任 manifest，抽样率 5%
- 中信任（50-79分）：提高抽样率至 30%
- 低信任（<50分）：全量扫描或拒绝 high/critical 任务

**影响范围**: RFC-003 §5.5-5.6（已写入）、DeepSeek Harness 插件、Hub 验证逻辑、manifest schema

**计划**:
- 阶段二：定义 manifest JSON Schema，Hub 实现第一层验证（签名+版本+时间戳+哈希抽样）
- 阶段四：DSH 插件实现 manifest 生成和本地扫描
- 企业版：第二层环境健康声明
- 远期：第三层 TPM 远程证明

**状态**: ✅ RFC-003 §5.5-5.6 已写入设计；schema 和实现待阶段二开发

### P3 — 远期，有真实部署经验后再写

#### P3-1: 储能协同调度 RFC

**背景**: battery 目前只是资源表的一个类型，没有定义储能充放电策略如何与任务调度联动。这是与储能厂商合作的核心。

**需要定义**:
- 储能充放电决策逻辑（什么时候充电、什么时候放电）
- 储能 SOC 如何影响任务调度（SOC 低时不能放电供高优任务）
- 储能+算力协同场景：负电价时充电+计算，高峰时放电供计算
- 储能参与需求响应的机制

**计划**: 阶段三 PoC 过程中积累经验，之后起草 RFC-007

#### P3-2: 安全模型操作细节补充

**问题**: RFC-003 偏概念，缺少任务数据加密、Server 侧隔离、结果验证等可操作细节。

#### P3-3: 算电协同的空间维度（跨区域路由）

**问题**: 当前设计主要考虑"时间维度"（等低价时段），但 NSW 电价高时 SA 可能负电价，调度应能跨区域路由任务。

**改进方向**:
- 明确资源表中 `price_per_mwh` 是节点所在区域的电价
- 调度器比较不同区域节点的总成本（含数据传输成本）
- 数据传输延迟和带宽作为跨区域调度的约束因素

**计划**: 有多区域节点后实现

---

#### P3-4: 结算与计量协议预留

**问题**: ROADMAP 说结算推迟，但协议层面应预留计量字段。

**需要预留**:
- 任务计量方式（GPU 小时？token 数？算力×时间？）
- 资源提供方的工作量证明机制
- 这些字段先在 compute-intent / 任务结果中预留，不实现

**计划**: 有真实交易需求后定义

---

#### P3-5: 协议一致性测试规范

**背景**: 协议要成为标准，需要有一致性测试（Conformance Testing）规范，定义"实现了哪些接口就算兼容 OCR 协议"。

**计划**: 有多个独立实现后再制定
