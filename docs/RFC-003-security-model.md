# RFC-003: 零信任安全模型

- **状态**: Draft
- **作者**: Open Compute Router Contributors
- **创建日期**: 2026-08-07
- **最后更新**: 2026-09-11

## 1. 摘要

本 RFC 定义 Open Compute Router 协议的**零信任安全模型**。核心原则：Hub 与 Server 之间默认不互信，必须通过强身份认证与最小权限授权建立信任；所有调度日志可导出用于第三方安全审计。

## 2. 设计动机

- **分布式拓扑风险**：算力节点分散在不同所有者与网络域，传统边界安全（防火墙/内网）无法建立统一信任边界。
- **多租户隔离**：不同企业的任务可能运行在共享算力上，必须防止跨租户访问。
- **数据主权**：企业数据不得离开其声明的安全边界。

## 3. 安全设计原则

### 3.1 零信任（Never Trust, Always Verify）

Hub 与 Server 之间默认不互信，必须通过 **mTLS/SPIFFE** 双向认证。身份以 SPIFFE ID 形式表达：

```text
spiffe://open-compute-router.org/hub/edge-01
spiffe://open-compute-router.org/server/region-ap-northeast-01
```

### 3.2 最小权限（Least Privilege）

任务仅能访问其声明的算力资源，禁止跨租户访问。授权模型：

- 每个任务绑定唯一的 SPIFFE ID（工作负载身份）
- 资源访问策略按任务维度下发，任务结束即回收
- Server 侧资源隔离（cgroup / 容器 / 虚拟机）

### 3.3 审计透明（Audit Transparency）

所有调度日志可导出用于第三方安全审计。

- 调度决策记录（谁、何时、调度到哪）
- 资源访问记录（哪个任务访问了哪些资源）
- 日志不可篡改，支持哈希链校验

## 4. 安全级别定义

| 级别 | 说明 | 典型场景 | 允许的节点 |
|------|------|----------|-----------|
| public | 公开数据，可运行于任何节点 | 通用推理、文档处理 | 公有 + 私有 |
| internal | 内部数据，限制在受信节点 | 企业内部应用 | 受信私有节点 |
| private_only | 私有数据，禁止路由至公有节点 | 商业数据、专有模型 | 仅私有节点 |
| confidential | 机密数据，需端到端加密与专属节点 | 金融、医疗、政务 | 专属隔离节点 |

> **关键约束**：`security_level: private_only` 的任务禁止路由至公有节点，无论 SLA Tier 高低（见 RFC-002 §5）。

## 5. 数据敏感度分级与分层认定

### 5.1 数据敏感度分级

除 `security_level`（安全隔离级别）外，协议支持 `data_sensitivity`（数据敏感度）字段，用于更精细的数据治理。两者关系：`security_level` 决定"能在哪些节点跑"，`data_sensitivity` 决定"需要什么级别的保护和脱敏"。

| 级别 | 说明 | 典型数据 | 强制约束 |
|------|------|----------|---------|
| `low` | 公开数据，无敏感信息 | 公开数据集、通用模型权重 | 无特殊约束 |
| `medium` | 一般内部数据 | 企业内部文档、非核心业务数据 | 建议 private_only 节点 |
| `high` | 敏感数据 | 含 PII（身份证、手机号）、商业机密 | **强制** private_only 节点 + 脱敏管道 |
| `critical` | 高度机密数据 | 医疗记录、金融交易、政务数据 | **强制** confidential 级别 + 端到端加密 + 专属节点 + 脱敏 |

> 字段定义见 `spec/compute-intent.schema.json` 的 `data_governance.data_sensitivity`。

### 5.2 分层认定原则：客户端引导，服务端强制

数据敏感度的认定采用**分层设计**，客户端（终端插件）做前置引导，Hub（服务端）做最终强制认定。

```
[终端插件 / 客户端]                    [Hub / 服务端]
       │                                    │
       │  1. 用户选择优先级/时间窗口         │
       │  2. 自动扫描本地数据，提示敏感度     │
       │  3. 填入 Compute Intent 字段        │
       │──────────提交任务──────────────────▶│
       │                                    │  4. Hub 对输入数据做 DLP 检测
       │                                    │  5. 比较：Hub检测 vs 用户声明
       │                                    │  6. 若 Hub 检测更高 → 强制升级
       │                                    │  7. 按最终级别强制路由约束
       │                                    │  8. 记录审计日志
```

**客户端（终端插件）职责**：
- 提供友好界面让用户选择优先级、时间窗口、网络亲和性
- 自动扫描本地输入文件，检测潜在敏感信息（PII、医疗数据等），提示用户
- 将用户选择和检测结果填入 Compute Intent 对应字段
- **性质：建议性的**，用户可以调整

**Hub（服务端）职责**：
- 对任务输入数据做自动 DLP 检测（扫描数据引用、元数据、样本）
- 比较 Hub 检测结果与用户声明的敏感度
- **若 Hub 检测到的敏感度高于用户声明，以 Hub 为准，强制升级**
- 按最终敏感度级别强制执行路由约束（high→private_only，critical→confidential）
- 记录完整审计日志：用户声明值、Hub 检测值、最终级别、路由决策

**协议层职责**：
- 定义 `data_sensitivity`、`data_masking_required`、`data_residency` 等字段
- 定义强制约束规则（如 high 级别必须 private_only）
- 规定"服务端检测结果优先于客户端声明"的原则
- **不规定具体检测算法**，DLP 实现由各 Hub 实现自行决定

### 5.3 为什么不能只信客户端

- 客户端声明可被用户手动修改或绕过
- 不同客户端插件的检测能力参差不齐
- 合规要求必须有服务端的强制校验和审计记录
- 类比：机场值机柜台可以帮你选座位，但登机口必须核验登机牌和身份

### 5.4 脱敏管道

`data_masking_required: true` 时（high/critical 级别默认开启），任务数据在进入执行节点前必须经过脱敏处理：

- **脱敏方式**：PII 替换/匿名化、字段级加密、令牌化
- **脱敏位置**：Hub 侧脱敏代理，或支持脱敏的受信节点
- **审计**：脱敏操作记录日志，包括脱敏规则、处理的数据量
- 具体脱敏算法和工具由实现层决定，协议只定义"必须脱敏"的约束

### 5.5 客户端敏感度清单（Manifest）

为解决"Hub 检测敏感度需要读取数据内容"与"高敏感数据不出域"之间的矛盾，协议支持客户端生成**敏感度清单文件**（Manifest），Hub 优先读取清单而非扫描内容。

#### 5.5.1 清单格式

清单为 JSON 文件，默认命名 `.ocr_manifest.json`，放置于数据集根目录：

```json
{
  "manifest_version": "1.0",
  "scanned_by": "dsh-ocr-plugin",
  "scanned_at": "2026-09-11T10:30:00Z",
  "plugin_version": "0.1.0",
  "overall_sensitivity": "high",
  "files": [
    {
      "path": "data-001.parquet",
      "sha256": "a1b2c3...",
      "size_bytes": 104857600,
      "sensitivity": "high",
      "detected_types": ["pii:id_card", "pii:phone"],
      "confidence": 0.92
    }
  ],
  "client_env": {
    "plugin_name": "dsh-ocr-plugin",
    "plugin_version": "0.1.0",
    "plugin_signature": "base64...",
    "os": "macOS-14.5",
    "hostname_hash": "sha256:..."
  },
  "signature": "base64-encoded-ed25519-signature"
}
```

字段说明：
- `overall_sensitivity`：整个数据集的综合敏感度级别（取所有文件的最高级别）
- `files[].sha256`：文件内容哈希，用于验证文件未被篡改
- `files[].detected_types`：检测到的敏感数据类型（不包含原文，只记录类型）
- `client_env`：客户端环境声明（见 §5.6）
- `signature`：清单的数字签名（企业版可选，用于验证清单来源可信）

#### 5.5.2 Hub 侧验证流程

Hub 收到任务后，按以下优先级处理：

1. **读取清单**：检查数据集目录中是否存在 `.ocr_manifest.json`
2. **验证签名**（如有）：用插件公钥验证清单签名，确认来源可信
3. **抽样哈希验证**：随机抽取 5-10% 的文件计算 SHA256，与清单中记录的对比
   - high/critical 级别抽样率提高到 50% 或全量
4. **信任标注**：验证通过后，Hub 信任清单中的敏感度标注，不扫描文件内容
5. **兜底扫描**：无清单、签名无效、或哈希验证失败时，Hub 执行内容扫描

#### 5.5.3 设计原则

- **不使用文件系统 xattr**：跨平台（Linux/macOS/Windows）和网络文件系统对 xattr 支持不一致，传输中易丢失。清单文件随数据集一起传输，更可靠
- **元数据优先，内容按需**：大部分场景 Hub 不触碰用户数据内容，保护数据主权
- **可验证而非盲信**：哈希和签名提供可验证性，防止用户手动篡改标注
- **渐进信任**：验证越充分，Hub 对清单的信任度越高（见 §5.6）

### 5.6 客户端环境证明与信任分级

清单签名只能证明"文件是插件生成的"，不能证明"生成它的插件和运行环境未被篡改"。协议定义**客户端环境证明**机制，Hub 根据证明结果对客户端进行信任分级。

#### 5.6.1 三层证明机制

| 层级 | 证明内容 | 实现方式 | 适用版本 |
|------|---------|---------|---------|
| **第一层：插件身份与完整性** | 插件签名、版本、扫描时间 | manifest 中的 `client_env` 字段 + 签名验证 | 开源版 |
| **第二层：环境健康声明** | OS 版本、是否 root/越狱、调试器检测、规则库版本 | 插件主动报告，Hub 校验 | 企业版 |
| **第三层：硬件远程证明** | 启动链完整性、TPM/Secure Enclave 证明 | TPM 2.0 远程证明 | 远期/高安全场景 |

#### 5.6.2 第一层：插件身份与完整性（必须）

Hub 验证以下内容：

- **插件签名**：manifest 的 `signature` 字段是否由官方插件私钥签名
- **插件版本**：`plugin_version` 是否在 Hub 维护的支持列表内（过旧版本可能有漏洞，不信任）
- **时间戳**：`scanned_at` 是否在合理时间范围内（默认 72 小时，防止重放旧清单）
- **规则库版本**：扫描时使用的检测规则库版本是否过旧

这一层防止"用户自行编写假插件生成假清单"。

#### 5.6.3 第二层：环境健康声明（企业版）

插件主动报告运行环境状态，Hub 据此评估环境可信度：

| 检测项 | 说明 | 高风险信号 |
|--------|------|-----------|
| OS 版本/补丁级别 | 操作系统版本和最新补丁 | 超过 N 个月未更新 |
| 是否 root/越狱 | 设备是否获取最高权限 | root/越狱设备上插件可能被注入 |
| 调试器检测 | 插件运行时是否有调试器附加 | 可能被运行时篡改扫描逻辑 |
| 规则库完整性 | 检测规则库的哈希是否与官方一致 | 规则库被替换可能导致漏检 |
| 插件二进制完整性 | 插件可执行文件的哈希 | 二进制被篡改 |

#### 5.6.4 第三层：硬件远程证明（远期）

使用 TPM 2.0 或 Apple Secure Enclave 进行远程证明：
- 设备启动时测量启动链（固件 → Bootloader → OS → 应用）
- 生成不可伪造的证明报告
- Hub 验证报告，确认从启动到插件运行的整条链路未被篡改

此层开发成本高、跨平台复杂，仅对 `confidential` 级别任务或有明确合规需求的客户启用。

#### 5.6.5 信任分级与 Hub 行为

Hub 根据证明结果计算客户端信任分，调整验证策略：

| 信任级别 | 条件 | Hub 行为 |
|---------|------|---------|
| **高信任**（≥80分） | 插件签名有效 + 版本受支持 + 环境健康 + 规则库最新 | 完全信任 manifest，抽样率 5%，不扫描内容 |
| **中信任**（50-79分） | 签名有效但环境有小问题（如 OS 稍旧、规则库非最新） | 提高抽样率至 30%，重点扫描高风险文件 |
| **低信任**（<50分） | 签名无效、版本过旧、或环境异常 | 不信任 manifest，执行全量内容扫描；high/critical 任务可能被拒绝 |

**核心原则**：信任是渐进的，不是二元的。验证越充分，Hub 对客户端标注的信任度越高，对数据内容的触碰越少。

## 6. 传输安全

- **端到端加密**：任务数据与结果传输使用 TLS 1.3。
- **机密任务**：`confidential` 级别任务要求节点级加密（TPM/HSM 密钥保护）。
- **密钥轮换**：短期证书（SPIFFE SVID）自动轮换，默认 24 小时。

## 7. 安全合规

所有 SLA Tier 的任务均受本安全模型约束。安全与调度解耦：安全策略由身份与数据分级决定，调度策略由时效与成本决定，二者在 Hub 侧统一裁决。

## 8. 漏洞披露

安全漏洞请遵循 [SECURITY.md](../SECURITY.md) 私密披露流程，请勿在公开 Issue 中报告。
