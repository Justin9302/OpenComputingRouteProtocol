# 现有 RFC 增补说明（Amendments）

- 状态：**Draft（修订建议）**
- 日期：2026-10-09
- 作用对象：RFC-002、RFC-003、RFC-005、RFC-006

本轮市场化补全（RFC-007~011）要求现有 RFC 做四处修订。以下按 RFC 给出增补段落，可直接并入原文。

---

## A1. RFC-002（时效分级调度模型）增补：置信度分级

**增补位置**：§4 新增小节"4.x 置信度与承诺等级"。

> Tier 不仅是调度优先级，还是**信息承诺等级（confidence level）**，用于定义预测推送（RFC-009）的可信度与撮合（RFC-008）的容量类别：
>
> | Tier | 承诺等级 | 容量类别 | 变更规则 |
> |---|---|---|---|
> | T0-T2 | **硬承诺（hard）** | 仅 hard_kw（确定性容量） | 取消/变更需付费（违约金进结算） |
> | T3-T10 | **软计划（soft）** | 允许 soft_kw（弹性容量） | 可随时调整，无违约金 |
>
> 含义：T0-T2 的任务对机房是可依赖的确定性负荷（机房据此做确定性储能准备）；T3-T10 是机会性负荷（机房只做计划性准备）。Tier 同时是**撮合 QoS 类**（RFC-008 §3 排序过滤条件）。

## A2. RFC-003（零信任安全模型）增补：控制边界与 IT/OT 分层

**增补位置**：新增章节"控制边界（Control Boundary）"。

> 1. **协议永不直接控制 PCS/储能/柴发等物理设备**。直接控制电网耦合设备 = 层级错误（OT 物理层暴露给开放网络），并产生电网合规责任。OCRP 的指令止步于**机房管理平面接口**，物理设备控制权完全留在机房 EMS 内。
> 2. **信息流双向、控制流单向**：
>    - 上行遥测（RFC-007 能力上报、RFC-010 信任事件）：只读，机房 → Hub。
>    - 下行情报（RFC-009 净负荷预测）：只读，Hub → 机房。
>    - 双向都不是指令；任何一方都不能通过 OCRP 改变对方设备的运行状态。
> 3. **IEC 62443 zone 映射**：OCRP 运行在机房"管理平面"（Zone 2，IT 侧）；PCS/储能控制（Zone 4，OT 侧）与 OCRP 之间由 zone 隔离 + 白名单适配器（fail-closed）隔开。
> 4. 演进路径：先单向信息（零攻击面）→ 机房具备响应能力且建立信任后，再演进双向协商（RFC-008 未来工作"多轮撮合"），控制流仍不进入 OT。

## A3. RFC-005（设备级自治与资源表）增补：字段标准化与收敛机制

**增补位置**：资源表结构定义与更新规则两处。

**字段标准化（资源表条目）**：

```
destination: 机房 / Router ID
capacity_profile: [{time_slot, avail_kw, hard_kw, price_floor, green_ratio, gpu_type, gpu_count}]
committed: [{task_id, slot_start, slot_end, kw, tier}]   ← 防超卖锁定
metrics: {power_cost, latency, green, utilization, trust}
status: active | reserved | committed | maintenance | draining
```

**收敛机制明确为链路状态 + 增量更新**：

- 每个 Router 是本地链路状态（LS）节点，Hub 是区域骨干（ABR）。
- 更新分两类：**事件触发增量**（签约/电价变化，带 version 号去重）与**周期全量快照**（15 分钟对账）。
- **明确不采用距离矢量**（RIP 式）：权重（电价）5 分钟级变化，距离矢量的慢收敛（计数到无穷问题）在高频更新下风险不可接受。
- 对外广播 = RFC-007 CapabilityReport（资源表的外部视图）。

## A4. RFC-006（任务执行与生命周期协议）增补：撮合后完整闭环

**增补位置**：状态机入口阶段。

```
原有：intent → 调度 → 执行 → 完成
修订：intent → 撮合(reserve) → 确认(committed) → 预测推送(RFC-009) → 执行 → 结算(RFC-011) → 释放 → 回 RFC-007 能力上报
```

状态机新增两个前置状态：

| 状态 | 定义 | 超时/违约处理 |
|---|---|---|
| `reserved` | 撮合成功，容量锁定待确认 | TTL 5 分钟；超时释放回池，通知用户 |
| `committed` | 用户/机房双方确认，签约生效 | 取消需违约金（RFC-010/011） |

**数据流闭环**：执行完成 → 结算单生成 → 信任分更新（RFC-010）→ 容量释放 → 能力上报更新（RFC-007）——**整个市场闭环无断点**。

## 修订优先级

| 增补 | 优先级 | 理由 |
|---|---|---|
| A3（RFC-005 字段+收敛） | **P0** | 撮合（RFC-008）依赖标准化的资源表字段 |
| A2（RFC-003 控制边界） | **P0** | 安全架构是全协议的地基，必须先行 |
| A1（RFC-002 置信度） | P1 | 预测推送（RFC-009）依赖置信度 |
| A4（RFC-006 生命周期） | P1 | 撮合成功后进入，闭环最后一段 |

建议修订顺序：A3 → A2 → A1 → A4，与 RFC-007/008 同步落地。
