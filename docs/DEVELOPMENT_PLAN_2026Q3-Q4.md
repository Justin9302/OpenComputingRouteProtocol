> **创建日期**: 2026-09-11
> **状态**: 待执行

> **工作节奏**: 业余时间，每周 10-20 小时，集中在周末

## 1. 项目现状

| 维度 | 现状 |
|------|------|
| 协议层 | RFC-001~011 全部 Draft：001-006 调度器形态 + 007-011 市场协议补全（能力上报/撮合出清/预测推送/信任/结算），spec 四份 |
| 代码层 | 5 个 Python 模拟器，全部是 mock，无真实网络通信；撮合闭环 mock（RFC-007/008）为下一开发项 |
| 数据层 | 电价是写死的模拟曲线，`--real` 参数未实现 |
| 供给侧 | 零真实节点 |
| 需求侧 | 零真实任务 |
| 产业合作 | 与某 PCS/系统集成商（台达 OEM，使用 ComAp EMS）达成初步合作意向 |
| 最后提交 | 2026-10-09（市场协议补全 RFC-007~011 + README 升级） |

**核心判断**: 最大的风险不是技术，而是冷启动。下一阶段的关键是从"写协议"转向"跑通一个真实闭环"。

## 4. 阶段一：设备级自治多节点原型

**目标**: 把 RFC-005 从单进程 mock 升级为 3+ 节点真实网络通信的可运行原型。

**为什么先做这个**: 设备级自治是项目核心差异化，必须尽早从概念变成可演示的东西。这个原型不需要 GPU，纯软件就能验证，是投入产出比最高的一步。

### 4.1 第 1 周：网络通信层 + Hub 角色澄清

**任务**:
- **[P0-2] 澄清 Hub 角色**：修订 RFC-001 和 RFC-005，明确 Hub 是逻辑角色而非物理中心，任何设备都可运行 Hub 功能。消除"三层架构"与"无中央控制器"之间的表述矛盾
- 设计节点间资源通告消息格式（对齐 `spec/resource-table.schema.json`）
- 用 Python `asyncio` + UDP 实现 P2P 通信（UDP 适合路由协议式的状态扩散，简单轻量）
- 每个节点启动后可向配置的邻居发送资源表更新
- 实现基础的消息序列化（JSON 或 MessagePack）

**交付物**:
- `src/ocr/node.py` — 节点基础类（监听、发送、邻居管理）
- `src/ocr/protocol.py` — 消息格式定义与序列化
- 测试：启动 3 个节点进程，A 发消息 B 和 C 能收到

**验证标准**:
```bash
# 终端1
python -m ocr.node --node-id node1 --listen 9001 --peers 127.0.0.1:9002,127.0.0.1:9003
# 终端2
python -m ocr.node --node-id node2 --listen 9002 --peers 127.0.0.1:9001
# 终端3
python -m ocr.node --node-id node3 --listen 9003 --peers 127.0.0.1:9001
# node1 发送一条资源通告，node2 和 node3 日志显示收到
```

### 4.2 第 2 周：资源表维护与老化

**任务**:
- **[P1-2] 资源表增加算力描述字段**：在 `spec/resource-table.schema.json` 中增加 `gpu_model`、`network_bandwidth_gbps`、`cpu_cores`、`ram_gb` 等字段，更新 RFC-005
- 重构 `ResourceTable` 类（从 `examples/resource-table-mock.py` 提取），支持网络同步
- 实现 TTL 老化机制（表项过期自动删除）
- 实现版本号/序列号（防止旧消息覆盖新状态）
- 节点收到资源通告后校验身份（简化版：信任配置的邻居，后续接 SPIFFE）

**交付物**:
- `src/ocr/resource_table.py` — 资源表核心类（upsert / prune / query）
- 节点收到更新后自动合并到本地资源表

**验证标准**:
- 插入一条 TTL=5s 的表项，5 秒后自动消失
- 发送 version=2 的更新，version=1 的旧消息不会覆盖
- `GET /resource-table`（本地 HTTP 接口）返回当前完整表

### 4.3 第 3 周：BGP 式扩散与收敛

**任务**:
- 实现路径向量（Path Vector）：每条通告携带经过的节点列表，防止环路
- 实现分裂水平（Split Horizon）：不从收到的接口发回同一表项
- 节点上下线自动收敛：邻居超时后标记为 down，相关表项逐步老化
- 触发更新（Triggered Update）：表项变化时立即通告，不等周期

**交付物**:
- 扩散算法集成到节点类
- 收敛测试脚本

**验证标准**:
```
拓扑: node1 -- node2 -- node3（链式）
1. node3 发布一条资源 → node1 最终能收到（经 node2 转发）
2. 杀掉 node2 → node1 上来自 node3 的表项在 TTL 后消失
3. 重启 node2 → 链路恢复，表项重新扩散到 node1
4. 全程无环路（日志中不会出现同一条消息无限循环）
```

### 4.4 第 4 周：电价数据被动接收

**任务**:
- 实现"数据源"角色：独立进程，模拟 AEMO 电价推送
- 节点配置 listen endpoint，被动接收电价数据（发布-订阅模型）
- 电价数据写入资源表的 `energy_grid` 类型表项
- 与阶段一的资源通告机制打通：节点收到电价后向邻居扩散

**交付物**:
- `src/ocr/energy_source.py` — 电价数据源（模拟 AEMO 推送）
- 节点支持被动接收外部数据推送

**验证标准**:
- 启动数据源进程，向 node1 推送电价
- node1 更新本地资源表，并向 node2/node3 扩散
- 所有节点最终都有相同的 `energy_grid/NSW1` 表项

### 4.5 第 5-6 周：Demo 打磨与文档

**任务**:
- **[P0-1] 起草 RFC-006 任务执行与生命周期协议**：定义 Hub↔Server 的任务下发、状态上报、数据传输、抢占与断点续传。阶段二开发前必须定稿
- 写一键启动脚本 `scripts/run-demo-autonomy.sh`（启动 3 节点 + 数据源）
- 写演示脚本：自动执行"节点加入→扩散→拔掉→收敛"全流程
- 录屏/截图素材
- 基于实现反馈修订 RFC-005（补充消息格式、扩散算法细节）
- 写技术博客草稿（"没有中央控制器的算力网络是怎么自治的"）

**交付物**:
- 可一键运行的 Demo
- 录屏视频（3-5 分钟）
- RFC-005 更新
- 技术博客草稿

**阶段一完成定义**: 陌生人看完 Demo 录屏后，能理解"设备级自治"是什么，并愿意尝试运行代码。

## 5. 阶段二：真实 AEMO 数据 + 端到端任务

**目标**: 算电协同从模拟曲线变成真实市场数据驱动，并跑通第一个真实任务。

**与阶段一的关系**: 阶段一第 4 周后可以并行启动阶段二。阶段二的 Hub 可以先不接入阶段一的分布式节点，先用中心化方式跑通，后续再融合。

### 5.1 第 1 周：AEMO 真实数据接入

**任务**:
- 调研 AEMO 公开数据接口：
  - AEMO MMS Data（`https://aemo.com.au/energy-data/electricity/aggregated-data`）
  - NemWeb 公开数据
  - 第三方开源 API（如 `opencorporates` / `aemo-data` Python 包）
- 实现 `energy-price-mock.py --real`：拉取 NSW1 真实 30 分钟粒度电价
- 数据缓存到本地 CSV，避免重复请求
- 验证数据质量：负电价时段数量、价格范围是否符合预期

**交付物**:
- `src/ocr/aemo_client.py` — AEMO 数据客户端
- `examples/energy-price-mock.py --real` 可用
- 真实数据 CSV 样本

**验证标准**:
- 拉取最近 7 天 NSW1 电价数据，包含至少若干个负电价时段
- 数据字段：time, price_per_mwh, region，与现有 CSV 格式兼容

### 5.2 第 2 周：最小 Hub 服务

**任务**:
- **[P1-1] 澄清 price_ceiling 语义**：明确定义为"任务总预算上限"（本币），调度器基于时间+资金双约束做资源匹配。更新 `compute-intent.schema.json`、RFC-002、demo-30s.py
- **[P2-2] 增加 estimated_duration 字段**：用户可声明任务预计执行时长，调度器用于判断能否在低价窗口内跑完
- **[P2-1] 调度器采用 SLA 策略组设计**：实时组/交互组/批处理组/离线组，每组一套调度逻辑
- **[P2-9] Manifest 验证（第一层）**：定义 `.ocr_manifest.json` JSON Schema；Hub 实现清单读取、插件签名验证、版本校验、时间戳防重放、SHA256 抽样验证；无清单时兜底扫描
- 把 `examples/hub-simulator.py` 重构为真正的 HTTP 服务（FastAPI 或 Flask）
- API 设计：
  - `POST /v1/tasks` — 提交算力意图（对齐 `spec/compute-intent.schema.json`）
  - `GET /v1/tasks/{task_id}` — 查询任务状态
  - `GET /v1/resource-table` — 查看当前资源表
- 调度逻辑：查询 AEMO 真实电价，结合 SLA Tier + 预算约束决定执行/等待
- 任务状态机：pending → scheduled → running → completed / failed

**交付物**:
- `src/ocr/hub.py` — Hub HTTP 服务
- 调度器模块 `src/ocr/scheduler.py`
- `spec/data-manifest.schema.json` — Manifest 清单 Schema
- `src/ocr/manifest_verifier.py` — 清单验证器（第一层）

**验证标准**:
```bash
# 启动 Hub
python -m ocr.hub --port 8080
# 提交任务
curl -X POST http://localhost:8080/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{"task_id":"test-001","compute_intent":{"type":"batch_processing"},"sla_scheduling":{"tier":"T9","price_ceiling":30}}'
# 查询状态
curl http://localhost:8080/v1/tasks/test-001
# Hub 日志显示：当前电价 X，高于 ceiling，任务 pending
```

### 5.3 第 3 周：最小 Worker + 端到端跑通

**任务**:
- 实现 Worker 进程：
  - 向 Hub 注册（上报算力资源）
  - 轮询/接收任务
  - 执行任务（调用用户指定的命令或脚本）
  - 上报执行结果和状态
- 第一个真实任务：CPU 可跑的轻量任务
  - 候选：数据集预处理（如清洗一个公开数据集）、向量索引构建（如用 faiss 建索引）、文件批量压缩
  - 选择标准：有明确输入输出、执行时间 10-30 分钟、可量化"完成了什么"
- 端到端联调：提交任务 → Hub 等待低价窗口 → 下发给 Worker → Worker 执行 → 返回结果

**交付物**:
- `src/ocr/worker.py` — Worker 进程
- 第一个真实任务脚本 `examples/tasks/data-preprocess.py`
- 端到端运行记录

**验证标准**:
- 提交一个 T9 任务，Hub 在电价低于 ceiling 时下发给 Worker
- Worker 真实执行任务，输出结果文件
- Hub 记录任务完整生命周期日志

### 5.4 第 4 周：量化与案例报告

**任务**:
- 收集端到端运行的完整数据：
  - 任务提交时间、调度时间、执行时段
  - 执行时段的真实电价（从 AEMO 数据取）
  - 假设白天高峰执行的电价（取同时段高峰均价）
  - 计算电费差异（按 Worker 所在节点的功率估算）
- 写案例报告：`docs/case-studies/first-real-task.md`
- 更新 README，加入真实运行截图/数据

**交付物**:
- 案例报告（含真实电价数据、省钱计算）
- README 更新

**阶段二完成定义**: 有一个真实任务在真实电价驱动下跑通，并有可引用的省钱数据。

## 6. 阶段三：储能联合 PoC

**目标**: 在真实/模拟硬件上验证"储能 + 算电协同"的商业闭环。

**前置依赖**: 阶段二完成（有可运行的 Hub/Worker），且合作方提供 ComAp 设备访问权限。

**注意**: 此阶段节奏依赖合作方，可能有等待期。等待期内继续推进阶段四。

### 6.1 前期准备（2 周，可与阶段二并行）

**任务**:
- 深入调研 ComAp API：
  - 注册 ComAp Developer Portal，获取 API 文档
  - 研究 WebSupervisor API 的认证方式（API Key + OAuth）
  - 研究可读取的数据点（SOC、充放电功率、电压、电流等）
  - 研究是否支持远程下发控制指令（充放电启停、功率设定）
- 写 `comap-adapter` 骨架：
  - `src/ocr/adapters/comap.py`
  - 实现身份认证 + 读取储能状态
  - 储能状态写入资源表的 `battery` 类型表项
- 明确 PoC 场景文档：
  - 场景：负电价时储能充电 + 同时跑低优训练；高峰时储能放电供计算
  - 接口需求清单（需要 ComAp 开放哪些数据点和控制指令）
  - 成功指标（电费节省比例、绿电消纳比例）

**交付物**:
- ComAp 适配器（读状态可用）
- PoC 场景文档 `docs/poc/storage-compute-cop.md`
- 给合作方的接口需求清单

**验证标准**:
- 用 ComAp 官方 API 测试账号（如有）或模拟器，能读取到储能 SOC 和功率数据
- 数据能写入 OCR 资源表

### 6.2 联合开发（4-6 周，依赖合作方节奏）

**任务**:
- 接入合作方提供的 ComAp 真实设备或测试环境
- 实现储能控制（如 ComAp API 支持）：
  - 充放电启停
  - 功率设定
  - 如果 API 不支持远程控制，通过 Modbus TCP 本地直连控制
- OCR 调度器与储能联动：
  - 负电价时段：指令储能充电 + 调度低优任务执行
  - 高峰时段：指令储能放电供计算 + 暂停/迁移低优任务
  - 储能 SOC 过低时：保护储能，停止放电
- 现场或远程联调测试

**交付物**:
- ComAp 适配器完整版（读+控）
- 储能联动调度策略
- PoC 测试报告（含数据曲线：电价、SOC、任务执行状态、电费累计）

**验证标准**:
- 连续运行 24-72 小时，记录完整数据
- 量化：相比"储能不参与、任务随时跑"，节省了多少电费
- 量化：绿电消纳比例提升了多少

### 6.3 PoC 成果包装

**任务**:
- 整理 PoC 数据为案例报告（中英文）
- 制作架构图和数据曲线
- 与合作方联合发布（博客 / 新闻稿 / 行业会议）

**阶段三完成定义**: 有真实硬件上的算电协同运行数据，可作为商业合作和融资的筹码。

### 7.4 客户端插件与工具生态

**目标**: 降低使用门槛，让用户在熟悉的工具链中直接使用 OCR，而不需要手动写 Compute Intent JSON。

**DeepSeek Harness 插件（优先级最高）**:

用户主力开发环境是 DeepSeek Harness（dsh），开发插件可以在用户提交训练任务时自动切入：

- **功能**:
  - 在任务提交界面增加 OCR 配置面板：优先级选择（Gold/Economy）、时间窗口、网络亲和性
  - 自动扫描训练数据/输入文件，检测潜在敏感信息（PII、医疗数据等），提示用户设置 `data_sensitivity`
  - **生成 `.ocr_manifest.json` 敏感度清单**：包含每个文件的敏感度级别、SHA256 哈希、检测类型、插件签名（对齐 RFC-003 §5.5）
  - 报告客户端环境信息（OS 版本、插件版本、规则库版本），用于 Hub 信任分级（对齐 RFC-003 §5.6）
  - 根据用户选择自动生成符合 `spec/compute-intent.schema.json` 的 Compute Intent
  - 调用 Hub API 提交任务，查询状态
- **定位**: 客户端做"前置引导"，Hub 做"强制认定"（见 RFC-003 §5.2）。插件的敏感度检测是建议性的，最终以 Hub 的 DLP 检测为准；但 manifest 有哈希和签名背书，Hub 验证通过后可不再扫描内容
- **开发时机**: 阶段二 Hub API 和 manifest 验证稳定后启动，预计 2-3 周
- **交付物**: `tools/dsh-plugin/` 插件包 + 使用文档

**其他客户端（远期）**:
- VS Code 扩展
- OpenAI 兼容 API 网关（让现有应用无缝接入）
- CLI 工具 `ocr-cli`

**设计原则**:
- 插件只负责"方便用户声明意图"，不做安全决策
- 所有客户端声明的字段，Hub 侧都要做校验和强制升级
- 协议层保持中立，不绑定特定客户端

## 8. 风险登记与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 业余时间不足，进度延迟 | 高 | 中 | 任务拆小，每个周末有明确交付物；允许阶段间滑动，不追求精确时间 |
| ComAp API 不支持远程控制 | 中 | 高 | 备选方案：Modbus TCP 本地直连；或只做"读状态+调度建议"，控制由人工/EMS执行 |
| 合作方节奏慢，PoC 迟迟不启动 | 中 | 中 | 先用 ComAp 官方模拟器/API 沙箱做技术准备；等待期推进阶段四 |
| AEMO 数据接入遇到 API 限制 | 低 | 中 | 备选：用历史数据 CSV 离线驱动；或第三方数据源（如 WattClarity） |
| 第一个真实任务"省钱"效果不明显 | 中 | 中 | CPU 任务功率低，电费绝对值小；用比例（节省 %）而非绝对值叙事；或用按需 GPU 跑一次训练任务放大效果 |
| 设备级自治原型性能差，无法扩展 | 低 | 低 | 原型阶段只验证机制，不追求性能；后续用 Go/Rust 重写关键路径 |
| 定制服务绑死客户，协议失去中立 | 中 | 高 | 严格分离：协议层（RFC/spec）不接受客户私有需求；定制代码放企业版/客户分支 |
| 负电价时段减少，叙事基础弱化 | 低 | 中 | 算电协同不只靠负电价，峰谷价差也有价值；NEM 未来 3-5 年负电价仍会频繁出现 |

## 9. 每周工作节奏

考虑到集中在周末工作，建议每个周末按以下节奏：

```
周六上午（3-4h）: 核心开发 — 写代码、跑测试
周六下午（2-3h）: 联调验证 — 跑通本周目标，记录问题
周日上午（2-3h）: 文档与整理 — 写文档、提交代码、更新进度
周日下午（1-2h）: 下周规划 — 拆任务，准备材料
```

**每周必须完成的事**:
1. 有代码提交（哪怕只是小改进）
2. 更新本计划中的进度标记
3. 如果有阻塞，记录下来并想备选方案

**每周不必做的事**:
- 不必追求完美，原型阶段能跑通就行
- 不必写详尽文档，关键接口有注释即可
