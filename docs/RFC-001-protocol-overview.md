# RFC-001: 协议总览与三层架构

- **状态**: Draft
- **作者**: Open Compute Router Contributors
- **创建日期**: 2026-08-07
- **最后更新**: 2026-10-10

## 1. 摘要

本 RFC 定义 Open Compute Router（OCR）协议的**总体架构与核心设计理念**。OCR 是一套轻量级、可演进的分布式算力路由协议，旨在解决 AI 算力需求爆炸与能源转型瓶颈交织背景下的**电力墙、安全墙、信任墙**三重约束。

## 2. 设计目标

- **中立**：不绑定任何芯片厂商、云厂商或 AI 框架。
- **安全**：基于零信任架构，支持私有算力隔离与端到端加密。
- **算电协同**：将计算任务与电力价格、绿电供给动态匹配，实现"算力跟着电力走"。
- **时效分级**：从 1 分钟实时底座到 24 小时离线批处理，用时间换取成本与能源的最优解。

## 3. 三层架构

```text
[用户层 / AI Agent]
       │  绑定 MCP，声明算力意图（显存、延迟、成本、安全、时效）
       ▼
[控制平面（Hub / Router / Server）]
       │  验证身份，解析意图，撮合匹配（intent × capability），
       │  绑定任务，单向推送净负荷预测 —— 信息流双向，控制流单向
       ▼
[Server 层 / 执行平面]
       │  执行计算任务，上报状态，本地对接电网开放数据
       ▼
[算力与电力资源池]  (GPU/NPU/微电网/储能)
```

> **关于控制平面的重要说明**：控制平面是一个**逻辑角色**，不是物理上的中央控制器。它由三种设备形态承载——**Hub（园区级·简易）、Router（组织内/广域·跨域路由）、Server（深度管理）**，职责一致、规模递增（详见 3.2）。在小规模部署中，控制平面可以是单台设备上的中心化实例；在大规模部署中，控制平面功能分布在多台设备上，调度决策基于各设备本地维护的资源表（见 RFC-005），不存在单一的控制中心。"三层"描述的是**职责分层**，而非**物理拓扑**。框架锚定图见 [SYSTEM_OVERVIEW.md](SYSTEM_OVERVIEW.md)。

### 3.1 用户层（User Layer）

AI Agent 通过 MCP 绑定声明算力意图（Compute Intent），包括：显存需求、延迟容忍度、成本上限、安全级别、时效分级。用户层不感知底层算力位置，只声明需求。

### 3.2 控制平面（Hub / Router / Server）

控制平面是协议调度的**逻辑角色**，负责：

- 验证身份（mTLS/SPIFFE）
- 解析算力意图
- 匹配能源策略（电价、绿电比例）
- 撮合匹配（intent × capability，多维权重排序）
- 绑定任务（reserve → committed，防超卖）
- 单向推送净负荷预测（RFC-009）
- 维护任务生命周期与审计日志

**设备形态与职责（参照网络设备分层，规模递增、逻辑一致）**：

| 形态 | 网络类比 | 部署规模 | 职责侧重 |
|------|----------|----------|----------|
| **Hub** | 集线器（简单、本地） | 园区 / 单机房内部 | 本地资源表维护、本地匹配、本地任务协调 |
| **Router** | 路由器（跨网段路由） | 组织内部或广域 | **跨域路由决策**：intent 该去哪个机房，跨机房/跨组织撮合 |
| **Server** | 服务器（深度应用/管理） | 全局 / 多组织 | 策略引擎、信任信誉（RFC-010）、结算（RFC-011）、预测分析、**全局出清** |

**关键认知**：**撮合是控制平面的职责，不是某一台设备的专属功能**——Hub 做园区级本地撮合，Router 承载跨域撮合，Server 承载全局出清与深度管理。职责按规模分布，协议接口（RFC-006）保持一致。

**部署形态**：
- **中心化部署**：单台设备运行控制平面（Hub 或 Server），管理所有 Server 节点。适合小规模、单组织场景，运维简单。
- **分布式部署**：多台设备各自运行控制平面功能（Hub/Router），通过资源通告（RFC-005）交换资源视图，协同调度。适合跨区域、多组织场景，无单点故障。
- **嵌入式部署**：控制平面功能嵌入 Server 节点或网络设备（Switch/Router）中，节点自调度。适合边缘计算和设备级自治场景。

### 3.3 Server 层（执行平面）

算力提供方，负责：

- 执行计算任务
- 上报实时状态（利用率、能耗、温度）
- 本地对接电网开放数据（AEMO、PJM、ENTSO-E 等）
- 响应抢占与断点续传

## 4. 核心概念

| 概念 | 说明 |
|------|------|
| Compute Intent | 用户声明的算力需求（见 spec/compute-intent.schema.json） |
| SLA Tier | 时效分级（T0-T10，见 RFC-002） |
| Security Level | 安全隔离级别（见 RFC-003） |
| Energy Plugin | 电网数据插件（见 RFC-004） |
| Resource Table | 设备级资源表：每台设备独立维护、类似路由表的「算力 × 能源」视图（见 RFC-005） |

## 6. 演进原则

- **协议先行，代码渐进**：先以 RFC 固化设计，再实现参考代码。
- **向后兼容**：新版本协议不得破坏已有任务声明格式。
- **开放演进**：任何贡献者均可提交 RFC 提案（见 CONTRIBUTING.md）。
